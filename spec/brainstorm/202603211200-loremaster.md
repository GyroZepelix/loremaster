# Loremaster — Cross-project skill manager CLI

## Step 0 — Session Initialization

**Idea:** A simple cross-platform CLI tool called "loremaster" that manages skills/commands for AI coding tools (Claude Code, OpenCode, etc.) across multiple projects. Each project has a `lore` file declaring which skills it needs and their sources (git URLs, local paths). Running `loremaster sync` fetches skills to `~/.local/share/loremaster/` and symlinks/copies them into the project. Skills are automatically excluded from git — both in project repos and in ~/.claude if syncing globally.

**Depth level:** Quick — the concept is well-scoped with clear boundaries (config file, fetch, symlink, gitignore).

**Initial understanding:** Loremaster solves the pain of manually keeping AI coding skills synced across projects while preserving privacy. Private skills live in private repos — anyone with access can `loremaster sync` themselves, but the skills never leak into project commits. Per-project `lore` files are the source of truth for which skills a project needs. Global ~/.claude skill sync is an option, with git-exclusion there too.

**Key constraints from user:**
- Per-project scope by default (lore file per project)
- Global `~/.claude/lore` file — same format, same sync behavior, no special "global mode" (UNIX philosophy: everything is a lore file)
- All synced skills excluded from git (project .gitignore AND ~/.claude .gitignore)
- Private repo support (git auth)
- Simplicity is paramount — do not overcomplicate
- UNIX philosophy: one mechanism, applied uniformly (project lore = global lore = same thing)
- Target audience: personal use + broader AI-coding community

## Step 1 — Context Extraction via Socratic Questioning

### Core Concept
Loremaster is a stateless Go CLI that reads a `lore.yml` file, fetches skills from git repos (or local paths) into a central store (`~/.local/share/loremaster/`), and symlinks or copies them into the appropriate AI coding tool's skills directory. Auto-detection determines the target tool; `loremaster init` bootstraps the config.

### Target Audience
Personal use first, then the broader AI-coding community.

### Known Constraints
- Simplicity is paramount — UNIX philosophy, one mechanism
- Relies on pre-existing git auth (SSH/credentials)
- Each `lore.yml` is independent — no cross-scope conflict resolution needed
- Provider-based architecture (claude, opencode) for target directory resolution
- Smart caching — `git pull` if already cloned, clone if not
- Monorepo is the primary skill source model

### lore.yml Format
```yaml
target: .claude  # auto-detected or set by `loremaster init`

skills:
  - name: commit-message
    source: git@github.com:user/my-skills.git
    path: commit-message       # subdirectory within the repo
    type: soft                 # symlink (default)
    ref: v1.2.0               # optional: git tag or commit SHA

  - name: frontend-design
    source: git@github.com:user/my-skills.git
    path: frontend-design
    type: hard                 # copy

  - name: local-experiment
    source: /home/user/dev/skills/local-experiment
    type: soft
```

### Provider Directory Mapping
| | Claude Code | OpenCode |
|---|---|---|
| Project skills | `.claude/skills/<name>/` | `.opencode/skills/<name>/` |
| Global skills | `~/.claude/skills/<name>/` | `~/.config/opencode/skills/<name>/` |

### Key Decisions
- **Language:** Go — single binary, zero dependencies, cross-platform, mature CLI ecosystem (cobra, go-git), scope-appropriate
- **Skill structure:** Directory with SKILL.md (compatible across Claude Code and OpenCode)
- **Lore file placement:** In `.claude/` or `.opencode/` syncs to sibling `skills/` dir; in project root auto-detects tool or asks via `loremaster init`
- **Link types:** `soft` (symlink, default) vs `hard` (copy) — per-skill config
- **Version pinning:** Optional `ref` field for git tag or commit SHA
- **Hard copy protection:** `sync` warns and skips if a hard-copied skill has local modifications
- **Registry/discovery:** Out of scope for now

### Assumptions
- SKILL.md structure is compatible across tools
- Users have working git SSH/credentials
- One repo can contain many skills (monorepo-first)

### Critical Unknowns
- Error handling strategy for partial sync failures
- Exact `loremaster init` interactive flow

## Step 3 — Problem Reframing and Jobs-to-be-Done

### JTBD Statement
> "When I **work across many projects that each need different combinations of my skills**, I want to **have them available without manual copying or config**, so I can **start prompting effectively immediately and keep my skill library evolving in one place**."

**Push factors:** Manual copy-paste across projects; skills drift out of sync; private skills risk leaking into project repos; no way to share a reproducible skill setup.

**Pull factors:** Single `loremaster sync` command; version-pinned skills; symlinks propagate upstream improvements automatically; clean separation of skill authoring and consumption.

**Habits:** Copy-paste is "good enough" for few projects; bespoke shell scripts; skills change infrequently once stable.

**Anxieties:** Breaking existing setup; tool disappearing (lock-in); symlink fragility across OS/filesystems; yet another tool to install.

### Reframing Insights
- **First Principles:** Skills are text files, git solves distribution — loremaster is just a declarative mapping from source to destination.
- **Inversion:** The lore file itself is the shareable artifact — it defines the skill *configuration*, not the skills.
- **Future-back:** `lore.yml` becomes a de facto standard like `.editorconfig`.
- **Hostile critic:** "Package management for 50-line markdown files" — countered by the multi-project, private-skill, drift-prevention use case.
- **Scale stress-test:** Led to repo-grouped skill format to avoid repetition at scale.

### Evolved lore.yml Format (Repo-Grouped)
```yaml
skills:
  - source: git@github.com:user/my-skills.git
    ref: v1.2.0
    include:
      - commit-message
      - frontend-design
      - code-review

  - name: local-experiment
    source: /home/user/dev/skills/local-experiment
```

### Problem Statement
AI coding skills are plain-text files that must land in specific directories, but there's no declarative way to specify which combination of skills each project needs and where they come from. Users with many projects and private skill repos resort to manual copying — causing drift, risking accidental commits of private skills, and making per-project skill sets tedious to manage. Loremaster is a minimal, git-native skill linker: a declarative mapping from source repos to destination directories, with repo-grouped skill selection and automatic git-exclusion.

## Step 10 — Final Synthesis and Articulation

### SWOT Analysis

#### Strengths
1. **Dead-simple mental model** — one YAML file, one command (`lore sync`), done
2. **Git-native** — leverages existing auth, repos, and versioning instead of inventing new infrastructure
3. **Zero runtime dependencies** — Go single binary, no package managers or interpreters needed
4. **Symlink-first design** — upstream skill changes propagate automatically without re-syncing
5. **Privacy by construction** — skills never enter project repos; auto-gitignore enforces this on every sync
6. **Uniform mechanism** — project lore and global lore use the same format and flow (UNIX philosophy)
7. **Repo-grouped YAML** — scales cleanly from 3 skills to 30 without repetitive source declarations

**Most critical:** Dead-simple mental model — if users can't explain it in one sentence, adoption dies.

#### Weaknesses
1. **Symlink fragility** — breaks across filesystems, doesn't work on some CI environments or Docker volumes
2. **No Windows support in v1** — excludes a meaningful user segment
3. **No registry or discovery** — users must already know skill repo URLs
4. **Git-only sourcing** — no HTTP tarballs, no inline skill definitions
5. **Silent gitignore mutation** — modifying `.gitignore` on every sync may surprise users who track it carefully
6. **Lock file is SHA-only** — no drift detection for hard-copied skills

**Most critical:** Symlink fragility — the core mechanism fails in the environments where reproducibility matters most (CI, containers).

#### Opportunities
1. **Growing AI coding tool market** — Claude Code, OpenCode, Cursor, Windsurf all use skill/prompt files with no package manager
2. **No incumbent** — nobody else is solving cross-project skill distribution yet
3. **Community skill sharing** — `lore.yml` files are inherently shareable, could seed a community ecosystem
4. **CI/CD integration** — `lore verify` could become a standard pre-flight check
5. **Convention-setting potential** — `lore.yml` could become the `.editorconfig` of AI skills

**Most critical:** No incumbent — first-mover advantage in a rapidly growing space.

#### Threats
1. **Tool vendors build it in** — Claude Code or OpenCode could ship native skill sync tomorrow
2. **Low switching cost** — a shell script can replicate core functionality for small setups
3. **Fragmented ecosystem** — each AI tool may diverge in skill directory structure, breaking the provider model
4. **Adoption chicken-and-egg** — without a critical mass of shared skill repos, the tool solves a niche problem
5. **Symlink hostility in containers** — Docker/CI friction could block the highest-value use case (reproducible setups)

**Most critical:** Tool vendors build it in — if Anthropic ships `claude skills sync`, loremaster's value proposition evaporates overnight.

### Final Articulation

#### The Problem
> "When I work across many projects that each need different combinations of my skills, I want to have them available without manual copying or config, so I can start prompting effectively immediately and keep my skill library evolving in one place."

#### The Solution
**Loremaster** is a stateless Go CLI that reads a `lore.yml` manifest (per-project or global), fetches skills from git repos into a central cache (`~/.local/share/loremaster/`), and symlinks them into the AI coding tool's skills directory. One command — `lore sync` — and every project has exactly the skills it declares, excluded from git automatically.

#### Differentiation
- **Declarative, not imperative** — a `lore.yml` file *is* the skill configuration, shareable and version-controlled
- **Git-native, not registry-dependent** — works with private repos, monorepos, and existing auth; no accounts, no publishing step
- **Tool-agnostic** — provider-based architecture supports Claude Code, OpenCode, and future tools via the same mechanism
- **Symlink-first** — upstream skill evolution propagates without re-syncing; hard copy available when isolation is needed

#### Riskiest Assumptions

| # | Assumption | Experiment |
|---|-----------|------------|
| 1 | Users have enough cross-project skill reuse to justify a tool | Survey 10 active Claude Code users — how many projects, how many shared skills, current sync method |
| 2 | Symlinks are viable in users' primary environments | Test on macOS, Linux, WSL2, Docker bind mounts, and 3 popular CI providers (GitHub Actions, GitLab CI, CircleCI) |
| 3 | AI coding tools won't ship native skill sync within 6 months | Monitor Claude Code and OpenCode changelogs; design loremaster to be complementary (multi-tool) rather than competing with any single vendor |

#### Strongest Counter-Argument
*"This is package management for 50-line markdown files — a shell script does the same thing."*

**Why the idea still works:** The shell script breaks down at scale — when you have 10+ projects, private repos with auth, version pinning, and need to prevent accidental commits of proprietary skills. Loremaster's value isn't the fetch-and-link operation (trivial) — it's the **declarative manifest** that makes skill sets reproducible, shareable, and auditable. The `lore.yml` file is the artifact, not the CLI.
